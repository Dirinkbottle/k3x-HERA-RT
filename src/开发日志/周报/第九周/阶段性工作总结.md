# 阶段性工作总结

> 本阶段完成 K3 AI 从 ONNX Runtime 调用入口、用户态运行时、内核设备通道到算子后端的首轮贯通；国庆前暂转为个人学习，节后继续推进板端验证与算子完善。

## 阶段成果

已建立从 ONNX 节点到 K3 内核任务的基本执行链路：Execution Provider 将可支持的节点转交给 K3 runtime，runtime 将节点描述和 tensor 元数据组织为图请求，通过 K3 AI runner 字符设备提交给内核；内核调度器随后将任务派发到 `k3_kernel_backend`。提交、完成等待和资源回收均通过统一的通道对象管理。

后端已具备 Conv2D、MatMul、逐元素算子、常用张量变换和部分神经网络算子的分发与校验框架。`AUTO` 目标现在在公共调用层统一归一化为 `PREFER_A100`，不会再被各算子静默解释为 CPU 路径；需要软件参考实现时必须显式指定 `PREFER_CPU`。这一约定使调度策略可预测，也便于定位 A100 后端尚未实现或执行失败的算子。

当前 A100 路径已经接入 int8 IME MatMul，并预留 FP16 IME 的 MatMul/Conv2D 调用入口。FP16 IME 依赖 `a100-fp16-ime` feature，默认关闭；在控制寄存器和数据布局尚未完全接入前，相关请求会明确返回“不支持”，而不是回退到 CPU。F32 的 A100 IME 路径同样尚待实现。

## 用户态运行时与 ABI

- `k3_aiRuntime/src/fronted/kd_uring.rs` 是用户态提交入口。`build_channel` 建立共享内存和设备通道，`submit_graph` 提交图描述，`wait_graph_complete` 等待完成事件；建议从这三个函数开始阅读调用链。
- `k3_aiUabi` 定义内核和用户态共用的描述符、属性、目标提示及 ioctl 编号。ABI 源码变更会反映到版本哈希，避免新旧结构体混用造成的静默错误。
- `k3_aiRuntime/src/ort_ffi.rs` 是 ONNX Runtime K3 EP 与 runtime 的桥接层。它会验证操作码、执行目标、tensor 个数、shape、连续 stride 和字节数，再将请求转为 `AiGraphNode`。当前 FFI 接口接受 dense、连续的 F32/F16 tensor 元数据；不满足布局或尺寸约束的请求会在提交前返回错误。
- `ort_test` 提供端到端验证程序，可通过带 K3 EP 的 ONNX Runtime 执行 FP16 YOLOv5 推理并完成图片标注。构建方式、交叉编译变量和部署步骤见 `ort_test/README.md`；本地 ONNX Runtime checkout 及其 CMake 产物不纳入版本控制。

ONNX Runtime 的 CPU EP 仍可承接 K3 EP 未声明支持的节点；但节点一旦已分配给 K3，执行期出错会直接返回失败，不能把该节点作为失败重试再交回 CPU。因此需要结合提交节点的操作码、节点编号和 backend 错误码定位问题。

## 算子后端

`k3_kernel_backend` 的公共入口先完成 ABI、属性大小、dtype、shape/stride、buffer 范围和别名检查，再按 `KernelOp` 分发。当前重点覆盖如下类别：

| 类别 | 已接入算子或能力 | 当前执行落点 |
| --- | --- | --- |
| 卷积与矩阵乘 | `CONV2D`、`MAT_MUL`，含 group/depthwise Conv2D 和可选 bias | CPU F32/F16、RVV/IME 路径；int8 IME 已接入，FP16 A100 IME 受 feature 控制 |
| 逐元素与归一化 | `ADD`、`SUB`、`MUL`、`DIV`、`MOD`、`SIGMOID`、`SILU`、`SCALE`、`RMS_NORM`、`ROPE` | CPU/RVV 为主，常用 F32/F16 路径已覆盖 |
| 张量与布局变换 | `CONCAT`、`TRANSPOSE`、`GATHER`、`GATHER_ELEMENTS`、`CAST`、`RESIZE`、`EXPAND`、`TILE` | RVV 或逻辑拷贝；reshape、slice 等 view 类操作由 frontend lowering 完成 |
| 常用网络算子 | `MAX_POOL`、`REDUCE_MAX`、`TOP_K`、`SOFTMAX`、`GLU` | 具备基础实现，复杂动态参数和特殊布局仍待补充 |

现阶段明确不覆盖 BF16、DMA/cache 同步、量化块布局、复杂量化 bias/scale 打包、cubic resize、动态 TopK/shape/scales，以及原地别名执行策略。这些边界会在后续扩展时与 A100 数据布局和内存管理一并处理。

## 内核设备与调度

板端支持仓库中的 `os/StarryOS/kernel/src/pseudofs/dev/accelerator` 新增 K3 AI runner 字符设备。用户态通过 `BUILD_CHANNEL` 和 `SUBMIT_GRAPH` 两类 ioctl 建立通道并提交图；内核侧验证共享区、登记图任务、唤醒调度器，并在完成后向用户态返回事件。调度日志保留 pid、token、节点编号及映射后的算子名称，便于把用户态请求与内核执行结果对应起来。

K3 专属调度器以每个 A100 核心对应一个 worker 的方式组织任务。图执行完成、失败或被取消时会更新节点状态、释放注册资源并通知等待方。与此同时，针对板端用户态取指异常和 cluster CPU 范围补充了适配，减少跨 cluster 调度和页故障地址处理带来的不确定性。

## USB 与 UVC 驱动

USB host 增加了类似 Linux USB ID table 的 interface 到驱动自动匹配机制，核心实现位于板端支持仓库的 `drivers/usb/usb-host/src/driver.rs`。枚举完成后，USB core 根据 VID/PID、interface class、subclass 和 protocol 生成匹配项，依次执行 driver `probe`；只有 probe 成功后才记录 interface 的逻辑认领，并在设备断开时调用对应的 disconnect 生命周期。

基于该机制，`uvcvideo` 薄驱动已能发现并逻辑认领测试摄像头的 Video Control 和 Video Streaming interface。摄像头的端口连接、描述符读取、interface 匹配和配置协商已验证；伪文件系统也已提供 `video0` 设备节点和基础 fd 操作接口。当前尚未得到完整视频帧，后续需要把异步 live device ownership、VC/VS 双 interface 管理、UVC format/frame descriptor 解析、等时 endpoint 配置和 payload 组帧接入完整生命周期。

## 后续计划

1. 完成 A100 FP16 IME 的控制配置、数据布局和板端正确性验证，补齐 F32 或明确其支持边界。
2. 使用端到端模型逐节点核对 K3 EP 的算子声明与 backend 覆盖范围，补充失败节点的可观测性与回归测试。
3. 继续完善通道取消、异常完成和多进程资源隔离，验证长时间、多图并发提交场景。
4. 完成 UVC 的异步 probe、格式协商和最小单帧采集，再扩展到稳定的视频流。
